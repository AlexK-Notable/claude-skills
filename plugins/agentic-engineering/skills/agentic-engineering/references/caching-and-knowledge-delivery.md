# Caching, Progressive Disclosure, and Memory Surfaces

## Why this chapter exists

The three topics share one problem: **a model's window is finite and expensive, but the knowledge an agent might need is unbounded.** Caching makes the *stable* part of context cheap to re-send; progressive disclosure loads knowledge *on demand*; memory surfaces move state *out* of the window and let the agent fetch it back. They are three answers to "how do I give an agent access to more than fits in its attention budget" — and they interact, since all three change what bytes appear where in the prompt, which is exactly what caching is sensitive to.

## T6.1 — Cache mechanics: the prefix-match invariant `[HIGH]`

**Prompt caching is a prefix match. Any byte change anywhere in the prefix invalidates everything after it.** Not Anthropic-specific: a peer-reviewed cross-provider audit (arXiv:2502.07776, Feb 2025) detected prefix-matched caching by timing side-channel at **Anthropic and OpenAI**, both sharing caches per-organization as published. DeepSeek is *not* in that result — per-user isolation hid the timing signal, so its mechanics are vendor-asserted rather than independently measured. OpenAI's docs: "Cache hits are only possible for exact prefix matches within a prompt." The outlier is **Google Gemini** — its reliable path is a *reference-object* model (pre-create a cache object, reference by ID) rather than in-band prefix marking; Gemini's implicit prefix caching had a documented reliability defect as of Dec 2025 (~42% hit rates on shared prefixes — googleapis/python-genai#1880).

For Anthropic-family APIs, render order is `tools → system → messages`; the cache key is the exact bytes up to each breakpoint.

### Design consequences

- **Stability ordering.** Order content by how often it changes: frozen system prompt and deterministic tool list first; per-session content next; per-turn content last; per-request volatiles (timestamps, UUIDs) at the end or eliminated. A 1,300-request controlled experiment on Azure OpenAI (ankitbko.github.io, Aug 2025) measured **71.3% per-request cost reduction and ~39% TTFT improvement** for stable vs perturbed prefixes; a production case study (ProjectDiscovery) recovered cache hit rates **from 7% to 84%** by relocating volatile working memory out of the prefix into the tail. `[HIGH]`
- **Append, don't edit.** Multi-turn agent loops cache well because they only append; rewriting earlier context — editing the system prompt mid-session, swapping tool sets, re-sorting history — pays full price for the whole suffix. OpenAI's Cookbook documents Codex as deliberately append-only, recommending `allowed_tools` over mutating the tool array; the ProjectDiscovery recovery above applies the same discipline to working memory. In "Don't Break the Cache" (arXiv:2601.06007, Jan 2026), the *cost* difference between strategies is small (2–4 percentage points, since the system prompt is cached under all of them) but the *latency* difference is large: on GPT-4o, naive full-context caching regressed TTFT ~8.8% vs 28–31% improvement for system-prompt-only and exclude-tool-results caching. Prefix discipline buys responsiveness more reliably than dollars — curation that mutates the prefix has a real, measured price (the flaw in naive "curate your context freely" advice), which is why platform mechanisms (tool search *appends* schemas; system messages *append* history) are all shaped as appends. `[CORROBORATED*]`
- **Economics differ by provider — don't universalize Anthropic's model.** `[VENDOR-DOC]` — figures as of **2026-08-08**; the fastest-drifting content here, so re-read pricing pages quarterly before any cost model depends on it.

  | Provider | Cache read | Cache write | TTL |
  |---|---|---|---|
  | Anthropic | 0.1× input price | 1.25× (5-min) / 2× (1-hour) premium | 5 min default, 1 h option |
  | OpenAI, GPT-5.6+ | ~0.1× (GPT-5.6 Sol: $5 → $0.50/Mtok cached) | **1.25× premium** | 30 min — `30m` is the only supported value |
  | OpenAI, GPT-5.x before 5.6 | ~0.1× | no premium (standard input price) | 5–10 min idle, 1 h max; 24 h extended on select models |
  | Google (explicit) | ~0.1–0.25× | reduced write + **hourly storage fee** | 60 min default |

  The OpenAI row is where stale knowledge bites hardest: the "no write premium" differentiator that distinguished OpenAI from Anthropic disappeared with GPT-5.6, and retention went from a 5–10-minute idle timer to a flat 30 minutes. Break-even: Anthropic and GPT-5.6+ OpenAI now share the same shape (1.25× write, ~0.1× read), so one cache hit beats sending the prefix twice uncached; Google's storage-fee model needs ~3–4 hits per 60-min window — low-frequency loops (e.g. an hourly scheduled agent) may lose money on it. Realized savings across the three providers on an agentic benchmark (500+ agent sessions, 10K-token system prompts): **41–80% cost reduction, 13–31% TTFT improvement** (arXiv:2601.06007).
- **TTL couples to loop pacing.** An agent that sleeps past the TTL re-reads its whole history cold (write-premium price instead of read — a 12.5× per-token swing on Anthropic). Pace within the TTL, or accept the miss consciously. **Live ops risk:** an unannounced server-side TTL regression (1 h → 5 min, Mar 2026, claude-code#46829) raised one production user's costs by **~26% in the affected month** (17% averaged across the two-month window, which understates the hit while live). Monitor `cache_type_1h` vs `cache_type_5m` ratios as a drift detector — TTL tier is infrastructure to observe, not assume. `[CORROBORATED*]`
- **Silent invalidators** (the checklist when hit rates are mysteriously zero): `now()`-style timestamps in the system prompt, random IDs early in content, non-deterministic JSON serialization (unsorted keys, set iteration), per-user interpolation into shared prompts, conditional system sections, per-user tool sets. Verify with usage fields: if `cache_read_input_tokens` stays zero across identical-prefix requests, diff the rendered bytes. `[VENDOR-DOC + community anti-pattern reports]`
- **Known subtleties** `[VENDOR-DOC — floors as of 2026-08-08]`: max 4 breakpoints per request; **minimum cacheable prefix is per-model** — Anthropic 512 tokens (Opus 5, Fable 5, Mythos 5) to 4,096 (Opus 4.5/4.6, Haiku 4.5), OpenAI 1,024 on GPT-5.6+ and 1,024–2,048 earlier, Gemini 2,048 on 2.5 and 4,096 on 3.x; under the floor, a prefix silently doesn't cache, no error returned. Breakpoints look back at most ~20 content blocks (tool-heavy turns need intermediate markers); parallel identical requests all miss until the first response streams (fan-outs: send one, await first token, fire the rest). Isolation is *organizational* only — caches never cross organizations, on most surfaces not workspaces either; that they're also **model-scoped** is our inference from KV-prefix keying, not documented `[SYNTHESIS]` — either way, run cheap sub-tasks in *subagents on the cheap model* rather than swap the main loop's model mid-session.

**Theory takeaway:** caching is a *physical constraint that shapes architecture*. The cheapest context is the context you never change — agent designs converge on an append-only transcript with stable preamble, and every context-management mechanism gets evaluated partly on whether it preserves the prefix.

## T6.2 / P2 — Progressive disclosure: knowledge on demand `[CORROBORATED* — cross-ecosystem]`

The pattern: keep a small, always-loaded *index* in context, and load full content only when the task calls for it.

- **Skills are the canonical implementation** — a folder with a `SKILL.md`; only the short description sits in context by default; the model reads the full file (and deeper references) when relevant. No longer vendor-only: the Agent Skills standard (open-sourced Dec 2025) was adopted within days by OpenAI (Codex/ChatGPT), Google (Gemini CLI), GitHub Copilot, Cursor, and VS Code; third-party marketplaces indexed 400K+ skills within three months.
- **It measurably works.** SkillFlow (UC Davis, arXiv:2504.06188): retrieving from a 36K-skill corpus raised Pass@1 **from 9.2% to 16.4% (+78% relative)**, reaching 84.1% of the oracle ceiling. The 9.2% arm has *no skills at all* — no load-everything arm is tested, so this shows retrieval helps, not that preloading hurts (that cost is in `tool-design.md`). SkillReducer (arXiv:2603.29919, 55K skills analyzed) names the mechanism "attention dilution" and found **60%+ of skill body content is non-actionable** — waste progressive disclosure keeps out of the window. For tools, on-demand retrieval beat static loading by **23–104% success-rate improvement** (DTDR, arXiv:2512.17052); see `tool-design.md` for the tool-catalog numbers.
- **Why it works** (theory, connecting to `context-degradation.md`): preloaded-but-unused knowledge occupies window, raises occupancy (weakening primacy attention, T2.3), and adds distractor surface (T2.5). Progressive disclosure converts a standing context tax into a per-use cost.
- **The index layer is a gate; the body is the signal.** `[CORROBORATED*]` SkillRouter (arXiv:2603.22455): description quality gates whether a skill *enters the candidate set* (26.4% of community skills lack routing descriptions entirely and are effectively invisible — SkillReducer), but **body content dominates final selection** — hiding the skill body costs **37–44pp** routing accuracy (figure as of 2026-08-08, moved between preprint revisions), far more than thinning descriptions. Description-rewriting studies show +11pp multi-step success and ~29% less degradation at 150+ tools (arXiv:2602.20426). Write descriptions with the trigger vocabulary the querying agent will actually use (lexical matching — T2.2), *and* invest in body quality; a perfect index over mediocre bodies caps out fast.
- **The trade-off — the knowledge-action gap.** `[MEDIUM]` A two-hop fetch the model must *choose* to make can be silently skipped. The closest direct evidence is LOCA-bench (arXiv:2602.07962): context-pressured agents stop after partial retrieval without fetching the remainder, plus practitioner reports of corner-cutting near window limits. The frequently-cited "knowledge-action gap" paper (arXiv:2508.13465) is *adjacent*, not this domain: it measures safety knowledge against safe execution, finding models answer risk questions correctly at >98% but act safely in instantiated trajectories at <26% — a suggestive analogue for "knows the rule, doesn't apply it under execution pressure," not a measurement of skipped documentation fetches; don't cite it as one. No published skip-*rate* for progressive disclosure exists yet. Mitigation: make on-demand loads structurally automatic (harness/hook-injected) where load-bearing, and loud when skipped.

## P2.1 — Just-in-time retrieval vs preloading `[MEDIUM]`

(Deliberately modest section — the evidence is directional, not airtight.)

When an agent has tools to fetch information (file reads, grep, queries, search), **prefer lightweight references + on-demand fetching over preloading everything potentially relevant — as a default, not a law.** What the evidence actually supports:

- **Focused beats bloated** `[MEDIUM]`: across 18 models on LongMemEval, focused ~300-token prompts substantially outperform full ~113K-token prompts (Chroma, 2025). Claude-family models showed the largest gap, driven by over-abstention under ambiguity. Caveat: this tests the *endpoint* (curated context wins), not the *mechanism* of getting there.
- **Tool-based fetching matches retrieval-preloading quality** `[CORROBORATED*]`: agentic keyword search reached >90% of vector-RAG performance with no vector store on general QA (Amazon Science, AAAI 2026); code-agent practitioners report embeddings "weren't the bottleneck" for code tasks — Claude Code dropped its early RAG implementation for agentic search (`[ATTRIBUTION]`, no published numbers; a vector-DB vendor dissents on token cost, so the latency/token trade is contested).
- **The vendor position is honest about its own evidence** `[VENDOR-DOC]`: Anthropic's just-in-time guidance (Sep 2025) is explicitly *unbenchmarked design advice*, flags that runtime exploration is slower than precomputed retrieval, and recommends **hybrids** — preload stable, reliably-needed context (the CLAUDE.md pattern); fetch dynamic content on demand.

What remains genuinely unknown: no neutral study isolates JIT fetching vs preloading with the final context held constant. Safe operating rule: **for agents with good search/read tools over dynamic content, just-in-time fetching is a reasonable default and rarely costs accuracy; preload only stable high-value context; go hybrid when latency matters or content is static.**

## T6.3 / P2 — Memory surfaces: state outside the window `[VENDOR-DOC + Opus probe 2026-06-13]`

Current vendor-supported lifecycle for long-running agents — three mechanisms with distinct scopes:

| Mechanism | Scope | What happens |
|---|---|---|
| **Context editing** | within session | Stale tool results / old thinking *pruned* (removed, not summarized); keeps transcript lean |
| **Compaction** | within session, near the limit | Earlier context *summarized* server-side into a compaction block carried forward |
| **Memory (files)** | across sessions | Agent reads/writes a persistent directory; survives restarts |

Design notes:

- **Memory is write-back, not write-once.** Useful patterns: scratchpads/notes maintained *while working*, and durable lesson/preference files consulted at session start. **The advice to hand-write a "check your memory file first" trigger is now obsolete on the Anthropic API** `[VENDOR-DOC — as of 2026-08-08]`: when the memory tool appears in a request's `tools`, the API adds the memory protocol to the system prompt itself, opening with "IMPORTANT: ALWAYS VIEW YOUR MEMORY DIRECTORY BEFORE DOING ANYTHING ELSE." and assuming context may reset at any moment. What's left to prompt is *scope* — bound what gets written to what you want persisted. Organization guidance (coherent directory, delete stale files) is already in the tool's description — reinforce only if it gets cluttered. Hand-rolling memory over your own file tools still requires supplying the trigger yourself, and the knowledge-action gap applies on the write path.
- **Retrievability rules apply to memory files** (T2.2): one fact per file with a summary line on top beats sprawling documents; verbatim IDs and consistent terminology beat elegant paraphrase; an index file pointing at atomic notes is progressive disclosure applied to memory.
- **Compaction is lossy and unaudited.** Anything that must survive verbatim (IDs, contracts, key decisions) belongs in a file or a re-injected anchor, not in trust that summarization preserves it.
- **Don't put secrets in memory or messages** — they persist in histories and summaries.

### Memory architecture: pick by history length, not by fashion `[MEDIUM]`

The decisive variable is whether the relevant history fits the context window:

- **If it fits the window, long-context beats an external memory layer on accuracy.** On LoCoMo, a GPT-5-mini long-context baseline beat the Mem0 pipeline by ~35 points (arXiv:2603.04814); memory's advantage at this scale is **cost, not accuracy** — it pays off past ~10 turns at 100K-token contexts (MEDIUM, single-source). LoCoMo (~20K tokens) is too short to even prove memory is necessary — the "Context Saturation Gap" (arXiv:2602.19320). `[MEDIUM for the accuracy gap; contested benchmark]`
- **When history genuinely exceeds the window, memory wins decisively.** On LongMemEval-M (>1M tokens) HINDSIGHT reached 83.6% with a 20B model vs a 39.0% full-context baseline (+44.6pp), gains concentrated in multi-session and temporal reasoning (arXiv:2512.12818) `[MEDIUM but vendor-affiliated]`. External memory is thus a remedy for *overflow*, not a general accuracy upgrade.
- **Graph-structured memory does not measurably beat well-managed flat or hierarchical notes for recall.** In a 12-method benchmark, tree-structured methods (MemTree, MemOS) came out ahead of the graph variant; the authors conclude *management strategy and information completeness matter more than representation type* (arXiv:2604.01707, v3 as of 2026-08-08) `[MEDIUM]` — graph extraction can lose information going in. The same benchmark shows the *backbone* matters more: moving 9B to 27B lifted multi-session scores over 1.6× for the strongest tree methods and temporal-reasoning F1 by over 10 points for others — before blaming your representation, check whether you're asking a small model to maintain structure it cannot. Reserve graphs for genuine multi-hop traversal needs.
- **The episodic/semantic/procedural split is the dominant vocabulary; the strongest empirical taxonomy paper *re-cuts* rather than rejects it** — arXiv:2602.19320 sorts systems into four structural types (Lightweight Semantic; Entity-Centric and Personalized; Episodic and Reflective; Structured and Hierarchical), keeping cognitive terms inside the categories while organizing by implementation shape. Use cognitive vocabulary for *what* is stored, structural types for *how*. The episodic→semantic *consolidation* pathway ("user corrected the date 3× → store the preference") is the agreed frontier, least implemented `[MEDIUM/aspirational]`.
- **The MemGPT/Letta lineage** (OS-style paged, self-editing memory blocks) is active: "sleep-time compute" (a second agent consolidates memory between turns) landed in 2025, git-backed MemFS in Feb 2026. But Mem0 (drop-in layer) has wider adoption than Letta (full runtime) precisely because it doesn't require rewriting the agent stack `[CORROBORATED* / vendor-only on specific numbers]`.
- **Budget for the dominant failure class: pollution → drift → conflict, a compounding loop** (SSGM, arXiv:2603.11768). Unconstrained semantic drift grows ~O(T) with interaction length; periodic reconciliation bounds it to ~O(N), the reconciliation window. SSGM mitigates at both ends — a write gate validating a candidate memory against existing ones for contradiction before consolidating, and a read gate filtering retrieval on access scope and freshness. Neither stage is claimed to dominate the other, so don't tune one and call it done `[MEDIUM — theoretical bounds]`.

Benchmark caveat: **LoCoMo scores are contested three ways, not two.** Zep published 84%; Mem0 re-ran the pipeline with the adversarial question category handled per spec and got 58.44%; Zep replied that Mem0 misconfigured it and that the corrected figure is 75.14%. An unresolved 84 / 75 / 58 spread for one system on one benchmark is the real lesson — and at ~20K tokens the benchmark is short enough to under-test memory in the first place. Prefer LongMemEval-M/V2 and always report cost alongside accuracy.

## T6.4 / P2.2 — Summarization strategy and its failure modes `[MEDIUM]`

When context must shrink, *how* you compress matters as much as whether you do. The evidence converges on a cascade and a set of guardrails.

**The cascade (cheapest-first):** mask or drop raw tool outputs → slide a window over old turns → invoke LLM summarization only as a last resort. On SWE-bench Verified, observation-masking *alone* cut cost 52% while raising solve rate 2.6%; the hybrid beat pure summarization on cost by ~11% (JetBrains, Dec 2025 — peer-reviewed, NeurIPS 2025 DL4C workshop) `[HIGH]`. Tool outputs are the dominant token sink and the safest thing to drop; agents rarely re-examine raw outputs.

**When you do summarize, make it query/task-aware, not generic.** Anticipating the downstream questions (Chain of Summaries) beat generic summaries by 9.6% F1 and even beat the *source document* (0.80 vs 0.76), at ~98% per-query token reduction (arXiv:2511.15719) `[MEDIUM]`. Recursive running-summaries (ReSum) add ~4.5% over append-everything ReAct, ~8.2% with a tuned summarizer (arXiv:2509.13313) `[MEDIUM]`. Agent-controlled curation beats fixed heuristics — a 14B learned curator beat a summarization baseline by ~9pp and outperformed a full-context 235B model at half the context (MemAct, arXiv:2510.12635) `[MEDIUM]`.

**Preserve verbatim:** architectural decisions, unresolved bugs, exact constraints, identifiers. **Discard:** redundant/raw tool outputs. Tune the compaction prompt for **recall first, precision second**. Both come from Anthropic's compaction guidance alone, not a JetBrains-corroborated convergence `[VENDOR-DOC]`. Offload durable facts to external notes you re-inject rather than paraphrase across rounds.

**Failure modes to guard against:**
- **Stop-signal erasure** — summaries smooth over the subtle cues that tell an agent to stop, so summarized trajectories ran 13–15% *longer* (JetBrains) `[HIGH]`.
- **Self-conditioning** — summarizing a context that contains the model's own earlier errors compounds them; additive to long-context decay and **not fixed by scaling model size**, though reasoning/thinking models largely avoid it (arXiv:2509.09677) `[HIGH]` — the mechanism behind "summary-of-a-summary" drift.
- **The accuracy tax** — condensation costs accuracy (full-context beat condensed memory by ~35 points on LoCoMo) in exchange for ~90% token/latency reduction; the accuracy figure traces to the same contested LoCoMo benchmark above, the reduction figure is vendor-asserted. Budget the trade deliberately `[MEDIUM]`.

To check a summary kept the load-bearing content, use **atomic-claim faithfulness (FactScore-style)** — an established metric, though its use here as a proxy for downstream success is less validated — not ROUGE overlap `[MEDIUM]`. Two honest gaps: no published per-round degradation *curve* for recursive summarization exists as of mid-2026 (mechanism attested, magnitude unquantified), and summarization hallucination rates are contested (0.7–1.5% grounded vs ~60% in one 2026 study) — don't cite a single rate.

## The composite picture

A well-engineered agent context, mid-2026: a frozen, cached preamble (system + tools); an append-only working transcript, pruned/compacted as it grows; knowledge held as a thin always-loaded index over on-demand bodies; durable state externalized to files engineered for lexical retrieval. Each piece exists because of a constraint documented elsewhere in this guide — prefix economics (here), attention mechanics (`context-degradation.md`), the finite-window thesis (`foundations.md`) — and the shape is now corroborated across providers and ecosystems, not just one vendor's docs.
