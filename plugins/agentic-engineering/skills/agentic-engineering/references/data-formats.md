# Token-Efficient Data Formats

Practice P2.3. Status: **complete** `[CORROBORATED* — Opus probe 2026-06-12; live-repo figures re-checked 2026-08-08]`. The question: when structured data must enter a model's window, which serialization minimizes tokens — and does compression cost comprehension?

## The three variables that decide it

Format choice is governed by **(a) data shape, (b) the specific model** (not merely its price tier — see below), **and (c) direction** (data going *into* the model vs the model *generating* the format). Generic "use format X" advice that ignores these is wrong somewhere.

## What the evidence shows

- **Compact formats deliver real savings on flat, uniform data — but the headline number depends on shape and on the baseline.** Against *pretty-printed* JSON the measured savings run roughly 15–65% by data shape, not a tight 30–60% band. TOON's own transparent benchmark (v4.1 README, figures as of 2026-08-08) reports **42.6% fewer tokens than JSON** at slightly better retrieval accuracy (72.2% vs 71.4%) — but this is measured on claude-haiku-4-5, gemini-3.6-flash, gpt-5.4-nano and grok-4.5, so it is not a "capable models" result. Against *minified* JSON the margin shrinks sharply (2,474 vs 2,892 tokens on that same benchmark) and on mixed-structure data narrows to about 1.6% — i.e. most of the headline is won against whitespace, not against JSON. CSV stays ~5–10% smaller than TOON on flat data (TOON's own flat track: 68,030 vs CSV's 64,247 tokens). A locally-measured 60–70% reduction is plausible as a best case but is shape- and tokenizer-specific — present such numbers as "measured on my tokenizer and my data," never as universal. `[CORROBORATED*]`
- **What breaks on nested data is generation and comprehension — not serialization size.** The strongest independent academic result (21-model benchmark, arXiv:2603.03306) is routinely misread. Its widely-quoted 3626-vs-1723 token gap is a **repair-loop total**, not a size comparison, and it belongs to the *invoice* case — one of the paper's TOON-**aligned** cases, not a nested one. What happened there: TOON's one-shot generation scored 0%, and because the system prompt carrying the format explanation is large, feeding the error history back for a repair attempt doubled total token usage versus JSON (3626 vs 1723). The paper names this the **repair loop tax**, alongside a **prompt tax** — a novel format needs a heavy instructional prompt whose overhead can negate syntax savings except at large data volumes. On the paper's genuinely deep-nesting case the size story runs the *opposite* way: TOON finished with both the fewest tokens and the highest accuracy (2,567 tokens / 48.6%) against plain JSON (3,575 / 43.8%). The real casualty is one-shot *generation* of nested structure — 0% for TOON vs JSON's 18.6% on non-aligned cases. `[CORROBORATED*]`
- **Independent nested-*retrieval* evidence points the same way, and it is the cleaner ballooning result.** improvingagents' nested run (GPT-5 nano) placed TOON last at 43.1% accuracy on 45,436 tokens — worse accuracy than Markdown's 54.3% on *fewer* tokens (38,357), and well behind YAML's 62.1%. Their summary: "we failed to find circumstances where TOON was the best-performing format". When shape is nested, a compact format can lose on both axes at once. `[CORROBORATED*]`
- **Terseness isn't the penalty — *unfamiliar* terseness is.** The key contrarian datapoint (independent 11-format benchmark, GPT-4.1-nano on 1,000 records): the *most* token-efficient formats scored *worst* on accuracy (CSV 44.3%, pipe-delimited 41.1%) while token-expensive familiar formats scored best (Markdown key-value 60.7%, at ~2.7× CSV's tokens; XML 56.0%, at ~3.9×). But the same run carries a counterexample the "compression costs accuracy" story tends to suppress: **Markdown-Table**, the second most token-efficient format tested, matched JSON's accuracy (51.9% vs 52.3%) on ~2.6× fewer tokens (25,140 vs 66,396). Terse *and* well-represented in training data is not a penalised combination. Caveat: single weak model; the community flagged exactly that limitation. `[CORROBORATED*]`
- **Model identity — not price tier — drives the format gap.** Strong models score near-100% across formats, reducing format choice to a pure token-cost decision, while weaker ones show large format-driven accuracy gaps. But the *tier* framing does not survive contact with the data: the June figures' "strong" group included gpt-5-nano, the cheapest model in the set, and TOON's current run (as of 2026-08-08) spans 57.0% (gpt-5.4-nano) to 97.1% (grok-4.5) *within* a single fast/cheap cohort. The genuine corroboration is arXiv:2601.12014, which benchmarks TOON generation across architectures and parameter scales and finds that "increased model capacity reduces this gap" — capacity, not price. `[CORROBORATED*]`
- **Inside agentic tool-call loops, accuracy-neutrality does not hold.** arXiv:2605.29676 (*Notation Matters*, revised Jun 2026 — after this file's probe) is the first evaluation of these formats end-to-end rather than on isolated comprehension or generation tasks. Across four agentic benchmarks (BFCL, MCPToolBenchPP, MCP-Universe, StableToolBench) and five open-weight models, TOON "achieves up to 18% reduction at a similar 9pp accuracy cost, but additionally cascades on multi-turn parsing failures and collapses parallel tool-call output for most models." Compression bought at the tool-call boundary costs accuracy in ways single-turn retrieval benchmarks cannot reveal. Scope caveat: open-weight models only, no frontier closed models. `[CORROBORATED*]`
- **Tokenizer caveat:** published savings are tokenizer-specific (most use OpenAI's o200k_base). Savings measured on one vocabulary don't transfer cleanly — re-measure on the target model's tokenizer via its token-counting API. `[MEDIUM]`
- **TOON itself** (github.com/toon-format/toon, spec **v4.1** as of 2026-08-08): real and fast-growing, with an unusually honest self-benchmark (it discloses CSV beating it on flat data and its own weak-model accuracy dips). Version figures here decay fast — the "v2.3" this file previously carried was the npm package version, not the spec, which was already v3.3 at the June probe and v4.1 two months later; re-check anything quoted from this repo before relying on it. Independent academic assessment, for complex state trees and DOM-like structures: "TOON is NOT in any way production-ready" — i.e. it's a tabular-input format, not a general JSON replacement. `[CORROBORATED*]`

## The selection rule

| Situation | Use | Why |
|---|---|---|
| Flat/uniform tabular → capable model | Compact tabular (TOON/CSV) | Real savings (~15–65% by shape), accuracy-neutral *for single-turn retrieval* — see the agentic-loop row |
| Flat tabular → weak/cheap model | Markdown-Table (Markdown-KV if accuracy is everything) | Terse *unfamiliar* formats measurably hurt weak-model accuracy; Markdown-Table is terse *and* familiar — JSON-level accuracy at ~2.6× fewer tokens |
| Nested / heterogeneous / optional fields | Minified JSON (or YAML) | Compact formats fail at generation on nested shape, and minifying JSON erases most of the token gap anyway |
| Model must *generate* the structure | JSON + constrained decoding / structured outputs | Compact-format generation is unreliable off-distribution (0% one-shot on nested structure) |
| Multi-turn agentic tool-call loop | JSON | ~9pp accuracy cost, parse failures cascade across turns, parallel tool-call output collapses (arXiv:2605.29676) |
| Accuracy dominates, tokens cheap | Familiar verbose (Markdown-KV, XML, JSON) | Training-distribution familiarity wins |
| Genuine tabular *querying* at scale | Don't put it in context — give the agent code/SQL | Contested practitioner consensus, but consistent with routing data through code (see `tool-design.md`) |

One connection to theory worth keeping in mind: compact formats strip the redundant scaffolding (repeated keys, punctuation) that — per the lexical-matching mechanism in `context-degradation.md` — sometimes *is* the retrieval signal. That's a plausible mechanism for why compression costs accuracy exactly where models are weakest, though it has not been directly tested — and Markdown-Table is the control case that complicates it, since it strips nearly as much scaffolding as CSV while holding JSON-level accuracy. Familiarity with the notation, rather than sheer volume of redundancy, is doing more of the work than the tidy version of this story admits.
